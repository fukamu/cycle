# Staging Light Terraform

This root module manages the Cloudflare Turnstile widget for `cycle.staging.fukamu.matoruru.com`. The Worker, Container image, static assets, custom domain, runtime secrets, and database migrations are application deployment concerns owned by Wrangler/GitHub Actions.

Terraform state uses the S3 backend against a manually bootstrapped, private R2 bucket. Repository secrets named `TERRAFORM_R2_ACCESS_KEY_ID` and `TERRAFORM_R2_SECRET_ACCESS_KEY` hold a bucket-scoped R2 Object Read Only credential for Plan. The same secret names in the `staging-terraform-apply` GitHub Environment hold a separate bucket-scoped R2 Object Read & Write credential; GitHub's environment-secret precedence gives only the Apply job the write credential. Workflows map the selected values to `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`. Never add credentials to `backend.hcl`, `terraform.tfvars`, shell history, or the repository.

R2 is strongly consistent and supports the conditional `PutObject` operations used by Terraform's S3 lockfile. Cloudflare documents R2 as a supported Terraform remote backend, but HashiCorp only tests the S3 backend against Amazon S3. R2 also does not provide S3-style object version history. Retain `use_lockfile = true` for Apply. Plan uses `-lock=false` because its credential is read-only; the shared `staging-terraform` workflow concurrency group serializes repository Plan and Apply, and concurrent manual remote operations are prohibited.

Immediately before Apply, `scripts/backup-and-drill-terraform-state.sh` pulls the live state, validates its envelope and size, computes SHA-256, and conditionally uploads the state and checksum under `fukamu-cycle/staging/state-backups/<commit-sha>/`. It reads both objects back, verifies their bytes, copies the verified state to an isolated `state-restore-drills` backend key, verifies that state again, and runs `terraform plan -refresh=false -lock=false`. The isolated state and lock objects are deleted; retained backup objects are never deleted automatically. Any snapshot, checksum, drill, or cleanup failure stops before Apply, and the helper contains no live-state push path.

`Terraform Plan Staging` creates a commit-bound saved plan after successful main CI. The configured owner approves it by manually dispatching `Terraform Apply Staging` with the Plan run ID. Apply verifies the actor, immutable artifact, and current main HEAD, then enters the `staging-terraform-apply` GitHub Environment before state recovery and application of that exact plan. A successful Apply triggers the migration-first Wrangler/Container deployment. Local Apply is not the normal release path.

The complete bootstrap, repository and Environment inputs, approval configuration, state recovery procedure, secret handling, and deploy sequence is in [`docs/deployment.md`](../../../docs/deployment.md).
